Workflow Integration Guide – MEMS.IAM

Detailed information about the workflow integration: key meanings, real-life examples, and suggestions for improvement.

1. Introduction

The MEMS.IAM workflow engine provides workspace-scoped approval and review workflows. You define workflow types (e.g. "Registration Approval"), add stages (e.g. "Initial Review", "Final Approval"), assign roles or users to each stage, then submit workflow instances linked to business records (e.g. a registration or document). Assignees see items in My tasks and can Approve, Reject, Return, Cancel, Claim, or Unclaim.

All endpoints are under: api/workspaces/{workspaceId}/workflows and require a valid Bearer token and workspaceId (GUID).

2. Key Concepts and Meanings

2.1 Workspace and scope

KeyMeaning
workspaceIdGUID of the workspace. Every workflow type and workflow instance belongs to one workspace. Used in the URL path for all workflow API calls.
Real-life useDifferent departments or clients each have their own workspace; workflows are isolated per workspace.

2.2 Workflow type (definition)

A workflow type is the template for a kind of process (e.g. "Registration Approval", "Document Review"). It has no stages until you add them.

KeyMeaning
workflowTypeIdGUID that uniquely identifies the workflow type within the workspace.
nameDisplay name (e.g. "Registration Approval"). Must be unique within the workspace.
descriptionOptional text describing what this workflow is for.
updateUrlOptional URL template for updating the business record from an external system. Placeholder {ReferenceId} is replaced by the workflow's reference ID. Example: https://service/module/update/{ReferenceId}.
viewDetailUrlOptional URL template for viewing the linked business record in the UI. Example: /registrations/{ReferenceId}. The API resolves this to a concrete URL (e.g. /registrations/REG-001) when returning workflow detail.
isActiveWhether the type is active. Inactive types may be hidden or not usable for new workflows, depending on backend.
stageCountNumber of stages attached to this type. A type with 0 stages cannot be used to submit a workflow (API returns "Workflow type has no stages").
dateCreated / createdByAudit fields for when and who created the type.

Real-life examples: Registration Approval (vessel/company registration); Document Review (compliance/contracts); Leave Request (manager → HR); Purchase Order (finance → director).

2.3 Stages

Stages are the ordered steps of a workflow type (e.g. stage 1 "Initial Review", stage 2 "Final Approval"). Order is determined by stageOrder (1, 2, 3, …).

KeyMeaning
workflowStageIdGUID of the stage.
stageOrderInteger order (1 = first, then 2, 3, …). Defines the flow.
stageNameDisplay name (e.g. "Initial Review", "Final Approval").
assigneesList of roles or users who can act at this stage (approve/reject).

Real-life examples: Initial Review (first-line checker); Final Approval (senior sign-off); Compliance Check (dedicated compliance stage).

2.4 Stage assignees

Assignees define who can act at a stage: either everyone with a given role or a specific user. For assigneeType: "Role", assigneeValue must be the WorkspaceRoleId (GUID).

KeyMeaning
assigneeType"Role" or "User".
assigneeValueFor Role: WorkspaceRoleId (GUID). For User: user GUID.
canApproveIf true, this assignee can approve (move to next stage or complete).
canRejectIf true, this assignee can reject (workflow completed as Rejected).

2.5 Workflow instance (submitted workflow)

A workflow instance is one run of a workflow type, tied to a business record (e.g. registration REG-001).

KeyMeaning
workflowIdGUID of the workflow instance.
referenceType / referenceIdBusiness entity type and record ID (e.g. "Registration", "REG-001"). Links the workflow to the actual record.
currentWorkflowStageId / currentStageNameCurrent stage; assignees at this stage see it in "My tasks".
statusPending, Approved, Rejected, or Cancelled. Only Pending workflows can be acted on.

2.6 Workflow actions

ActionMeaningWhen used
SubmitCreate a new workflow instance. Starts at the first stage.User submits a registration or document for approval.
ApproveApprove current stage; move to next or complete.Reviewer is satisfied and approves.
RejectReject the workflow. Status becomes Rejected.Reviewer rejects (e.g. incomplete documents).
ReturnSend back to a previous stage."Return for corrections" to an earlier stage.
CancelCancel a Pending workflow.Submitter or admin cancels the request.
Claim / UnclaimAssign or release the current user as the one working on this workflow at this stage.Optional; used when only one person should act at a time.

2.7 Activities (audit trail)

Each action creates an activity record: action, remark, createdBy, dateCreated, old/new stage. Used for compliance: "Who approved this?", "When was it returned?", "What was the reject reason?".

3. Real-life use cases (end-to-end)

  • Vessel registration approval: Type "Registration Approval" → Stages "Initial Review" → "Final Approval" → Roles "Registration Officer" then "Registration Manager". Submit REG-001 → Officers see in My tasks → Approve → Managers see → Approve or Reject.
  • Document compliance review: Type "Document Review" → "Compliance Check" → "Approval". Assignees: Compliance Officer, then Approver.
  • Leave request (HR): Type "Leave Request" → "Manager Approval" → "HR Approval". Employee submits; manager then HR approve or reject; Return sends back to manager.

4. API response wrapper

All endpoints return: success, data, message, code, error. On failure, error may contain e.g. "Workflow type has no stages" (MEMS001) or 403 Forbidden.

5. Suggestions and possible corrections

Backend: (1) Use WorkspaceRoleId (GUID) for assigneeValue when assigneeType is Role. (2) Resolve viewDetailUrl with {ReferenceId}. (3) Document updateUrl usage. (4) Consistent pagination parameter names.

Frontend: (1) Show role name (not GUID) for assignees. (2) Only allow submit for types with stageCount > 0. (3) Include updateUrl in Create/Edit type. (4) Use assignable-to-me for My tasks tab.

Documentation: State in API reference that assigneeValue for Role must be WorkspaceRoleId (GUID). Document common error codes and UI handling.
